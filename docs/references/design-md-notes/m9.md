### 和模块 2 完整色板的关系

【推断，依据是 m9 内部证据，没有对照 m2】：它是模块 2 的**摘要**，不是补充，而且是**不完整的摘要**。

- 证据一：色名带层级编号（IBM 的 Blue 60、Gray 100；Clay 的 Matcha 600；Composio 的 Border Mist 10；Mintlify 的 Gray 700），说明背后有更大的色板，这里只挑了几档。
- 证据二：同一节的示例提示词用到了速查表没列的颜色。提示词里共出现 286 个不重复的十六进制色值，其中 65 个（约 23%）不在本品牌的速查表里；55 家里有 29 家至少有 1 个。例子：Vercel 提示词里 8 个色值有 6 个不在速查表；Claude 的 Warm Sand（#e8e6dc）、Charcoal Warm（#4d4c48）、Warm Silver（#b0aea5）都只在提示词里出现；Expo 的 Input Border（#d9d9e0）同理。
- 结论：速查表只够写「背景 + 文字 + 一个强调色 + 边框」这种最简页面。真要写组件，AI 仍得回模块 2 查，或者照抄示例提示词里的值。它新增的唯一信息是「按角色排好的最短清单」，不新增任何颜色。

## 3. 示例提示词的写法规律

### 几条

- 56 家共 254 条。45 家是 5 条；5 家 4 条（BMW、Figma、Mistral AI、Sanity、SpaceX）；3 家 2 条（Coinbase、Revolut、Wise）；3 家 1 条（Intercom、Kraken、Miro）。
- 「5 条」是事实上的模板标准。

### 针对哪些组件或区块（按品牌数，分母 56）

| 对象 | 家数 | 备注 |
|---|---|---|
| Hero 首屏 | 53 | 其中 50 家把它放在第 1 条；没有的是 Airbnb、Sanity、Spotify |
| 卡片（功能卡、产品卡、内容卡） | 约 46–48 | |
| 导航栏 | 约 35 | 绝大多数是营销站顶部导航；侧边栏只有 Spotify、Kimi |
| 页面区块（深色区、功能区、信任条、数据条、交替布局等） | 约 33 | |
| 徽标 / 标签 / 小号大写标签 | 约 22 | |
| 单独的按钮 | 约 19 | 按钮更多是嵌在 hero 里顺带写 |
| 输入框 / 表单 / 搜索框 | 约 14–16 | IBM、Sanity、xAI、HashiCorp、Pinterest、PostHog、Spotify、Kimi 等 |
| 页脚 | 7 | MiniMax、Mistral AI、NVIDIA、OpenCode、Pinterest、Uber、Zapier |
| 代码块 | 约 5–6 | Composio、Expo、Ollama、Replicate、Resend（VoltAgent 嵌在 hero 里） |
| 标签页（tab） | 4 | Figma、MiniMax、Ollama、Zapier |
| 定价卡 | 1 | 只有 Framer |
| 命令面板 | 1 | 只有 Linear |
| 应用外壳（侧栏 + 主面板） | 1 | 只有 Kimi |
| 表格、弹窗、菜单、提示条、空状态、加载态、设置页 | 0 | 全节一条都没有 |

【推断】这套提示词是「营销落地页」视角：hero、功能卡、顶部导航占了大头。做个人工作台、浮窗工具这类交互产品最常用的组件（表格、列表、弹窗、菜单、表单校验、空状态）几乎没有可参考的样本。唯一接近的是 Kimi（应用外壳、聊天输入框）、Linear（命令面板）、Spotify（侧边导航）、Raycast（键帽）。

### 一条提示词里通常有什么

统一句式：动词（Create 106 条、Design 93 条、Build 54 条）+ 组件名 + 冒号或 on/with + 一串属性。按 254 条统计：

| 信息 | 出现比例 | 备注 |
|---|---|---|
| 字号（px） | 约 97% | 几乎每条都有 |
| 具体色值（hex/rgba） | 约 87% | 33 条完全没有色值 |
| 字体名 | 约 76% | |
| 圆角 | 约 72% | 含 pill、sharp corners 这类说法 |
| 字重 | 约 69% | |
| 字距 | 约 30% | |
| 内边距 / 间距 | 约 28% | |
| 行高 | 约 25% | |
| 阴影 | 约 20% | 给的时候常是完整多层值（Airbnb、Notion、Stripe、Vercel） |
| hover 状态 | 约 15%（37 条，25 家） | |
| focus 状态 | 7 条 | |
| active 状态 | 8 条 | |
| 禁用态 | 0 条 | |
| 明确宽高或列数 | 约 6%（16 条，12 家） | 多数提示词不写尺寸 |
| 界面文案 | 少数 | 如 Kimi 的中文占位文字、Mintlify 的按钮文字 |

- 每条平均带约 6 个具体数值（色值加 px 值，中位数 5.5）。
- 规律：**颜色、字号、字体、圆角是必写四项；间距、行高、阴影看情况；状态和尺寸大多不写。**

### 多长

- 平均 32 个英文词，中位数 30，范围 11–62 词。约一到三句话。
- 最长的是 Apple 的 hero（62 词）、VoltAgent、Lovable、xAI、Renault、Sanity（55–57 词）。最短的是小标签类（11–15 词）。

### 3 个具体到能直接执行的例子（转述）

1. **Kimi 聊天输入框**：宽 768px、高 130px、白底、24px 圆角、1px 25% 透明度的黑色描边、两层浅阴影；占位文字 16px（给了中文原文）；底部一行依次放工具小标签、模型选择器、36px 圆形发送按钮。好在哪：给了外框尺寸、内部结构顺序、真实文案，AI 不用猜布局。
2. **IBM 表单输入框**：#f4f4f4 底、0 圆角、高 40px、左右内边距 16px；上方标签 12px/400、字距 0.32px、#525252；底边默认 2px 透明、聚焦时 2px #0f62fe；占位符 #6f6f6f。好在哪：默认和聚焦两个状态都有值，组成部分（标签、输入区、占位符）逐一交代。
3. **Sentry 主按钮**：底色 #79628c、1px #584674 描边、内阴影给了完整值；文字 14px Rubik 700、白色、大写、字距 0.2px；圆角 13px；hover 时换成另一组完整的阴影值。好在哪：一个组件的全部视觉属性加一个状态变化，没有一个形容词需要解释。

同档次的还有 Linear 命令面板、Zapier 标签页（激活态和 hover 态用哪种内阴影下划线都写了）、Stripe 卡片（两层阴影全值）。

### 2 个空泛的例子（转述）

1. **Runway 信任条**：只说「单色公司 logo、横向排列、间距宽松、深色背景」。全条 0 个数值：logo 多高、间距多少、灰到什么程度都没说。
2. **Tesla 底部常驻栏**：说有聊天输入框、发送图标、带青色图标的次要按钮、贴在视口底部、白底。没有高度、字号、色值、圆角，「青色」也没有给值。

同类的还有 Lamborghini 导航栏（0 个数值）、Replicate 的 hero（只说橙红到品红的渐变，没给色标；两个按钮没给任何值）。另外，不少整体具体的提示词里也夹着模糊词，如「comfortably rounded」「subtle」「generous」「massive」，没有对应到数值时等于没说。

## 4. 迭代指南里写了什么

### 基本数

- 51 家，共 326 条；每家平均 6.4 条，中位数 6 条，范围 4（Revolut）到 10 条（xAI）。分布：5 条 12 家、6 条 17 家、7 条 10 家、8 条 10 家。
- 每条平均 13 个英文词，一句话。约 52% 的条目带具体数值（色值、px、字重）。约 31% 的条目带否定（never / not / no），约 16% 带强制词（always / must / non-negotiable）。
- 有 11 家在列表前加了一句相同的引导语，大意是「在修改用本规范生成的界面时」（Cal.com、Composio、Ferrari、Framer、Lamborghini、PostHog、Raycast、Renault、Superhuman、Tesla、VoltAgent）。

### 三套模板

读下来，51 家其实出自三套写法：

- **A 风格规则清单（约 34 家，占绝大多数）**：名字叫迭代指南，内容是 5–8 条品牌风格规则，例如 Apple、Stripe、Linear、Notion、Vercel、IBM。和迭代没有关系。
- **B 提示话术模板（12 家）**：教人怎么对 AI 提修改要求。Claude、Cohere、Composio、Expo、Ferrari、Framer、Lamborghini、Ollama、Renault、Tesla、Uber、VoltAgent。前几条高度雷同，后几条换成品牌规则。
- **C 核查清单模板（5 家）**：每条以 Verify / Check / Ensure / Confirm 开头，末条给一句整体调性。Cal.com、PostHog、Raycast、Superhuman、Framer。
- 例外：Sanity 写的是搭建顺序，共 7 步（先铺深色底 → 加表面和边框 → 上字体 → 点强调色 → 调间距 → 加技术标签 → 收尾检查），是唯一讲「先做什么后做什么」的。

### 跨品牌最常见的条目（按家数）

风格规则类（家数靠关键词加人工核对，都是「约」）：

| # | 条目类型 | 约多少家 | 例子 |
|---|---|---|---|
| 1 | 阴影和层级怎么做：多层阴影，或不用阴影、改用边框和底色分层 | 约 33 | 其中约 13 家是「不用阴影」（IBM、Ollama、OpenCode、Resend、Revolut、Sanity、SpaceX、Supabase、xAI、Zapier 等） |
| 2 | 强调色只用在指定位置、克制使用 | 约 30 | Airbnb、Apple、BMW、IBM、Linear、Notion、Zapier；Ferrari、Renault 写到「每屏只出现一处」 |
| 3 | 底色和冷暖基调：从哪种底色起手，不用纯白或纯黑 | 约 30 | 13 家用「先从某底色开始」的句式（Airbnb、Clay、Resend、Spotify、Supabase、xAI 等） |
| 4 | 圆角规则：全胶囊、零圆角或分档 | 约 30 | IBM 和 BMW 零圆角；Mintlify、Replicate 全胶囊；Expo 按组件分四档 |
| 5 | 字重只用两三档、各档管什么 | 约 28 | Linear、Mintlify、Vercel、Notion 的「读 / 交互 / 强调」分档 |
| 6 | 字距、行高随字号变化 | 约 27 | 7 家给了「字号 → 字距」对照（Apple、Cursor、Linear、Lovable、Mintlify、Notion、Vercel） |
| 7 | 字体分工：哪种字体管标题、正文、代码 | 约 26 | Resend、Zapier、Cursor 的「三种字体三种角色」 |
| 8 | 边框怎么做：透明度、颜色偏暖偏冷、用阴影代替边框 | 约 20 | Vercel、Linear、Resend、Zapier |
| 9 | 小标签用大写加字距 | 14 | HashiCorp、MongoDB、Sentry、Spotify |
| 10 | hover 和交互反馈怎么变 | 约 13 | Raycast 用透明度过渡；xAI 是变暗；Wise 是缩放 |

另有「图片或内容是主角，界面退后」约 10 家（Airbnb、BMW、Pinterest、Runway、SpaceX、Tesla、Spotify 等）；间距规则约 10 家；OpenType 字体特性 6 家（Clay、Linear、Raycast、Resend、Stripe、Wise）。

话术和流程类（这才是字面意义上的「迭代指引」）：

| # | 条目类型 | 家数 | 品牌 |
|---|---|---|---|
| a | 一次只改一个组件 | 12 | 模板 B 的 12 家 |
| b | 引用具体色名加色值，不说「弄灰一点」 | 10 | Claude、Composio、Expo、Ferrari、Lamborghini、Ollama、Renault、Tesla、Uber、VoltAgent |
| c | 感觉和数值一起说 | 7 | Composio、Expo、Ferrari、Lamborghini、Renault、Tesla、VoltAgent |
| d | 明确指定用哪种字体 | 约 7 | Claude、Cohere、Composio、Expo、Runway、Uber、VoltAgent |
| e | 阴影和光晕用规范里的命名来说，不说泛泛的「投影」 | 5 | Claude、Expo、Uber（阴影）；Composio、VoltAgent（光晕） |
| f | 用自然语言描述，不写 CSS 值 | 4 | Ferrari、Lamborghini、Renault、Tesla |
| g | 口语说法对应到 token | 1 | 只有 Composio：把「边框几乎看不见」对应到某两档边框 token |
| h | 核查式条目 | 5 家整段 | 模板 C 的 5 家；Renault、Tesla 各有 1 条 |
| i | 症状 → 修法（「如果显得…，就…」） | 约 9 | Cal.com（显得挤就加间距）、HashiCorp（阴影看得见就再减）、PostHog、Superhuman、Tesla、Ferrari、Ollama（显得花就删） |
| j | 整体调性一句话 | 3 | Cal.com、PostHog、Superhuman |

### 两个值得注意的问题

- **条目互相打架**：f 类 4 家要求「用自然语言，不写 CSS 值」，但这 4 家全都同时写了 c「感觉和数值一起说」，它们自己的示例提示词也带数值；而其余大多数品牌（Stripe、Linear、IBM 等）给的全是精确值。【推断】这是模板套用留下的痕迹，不是经过验证的做法。
- **话术类条目很少**：a–g 合计约 46 条，占 326 条的约 14%，而且集中在 12 家。其余约 86% 是风格规则的复述（h 类的核查句式，内容也还是风格值）。

## 5. 这一节普遍缺什么

站在「AI 写中文、只做电脑版的交互产品」的角度逐条判断。「材料里有没有」是事实，「为什么要紧」是【推断】。

| # | 该有的内容 | 材料里有没有 | 证据 |
|---|---|---|---|
| 1 | 规则优先级（冲突时听谁的） | **没有** | 全文没有 priority、conflict 这类词。最接近的是 11 家给个别条目标了「不可商量」或「必须」（Apple、BMW、Clay、Framer、IBM、Linear、Resend、SpaceX、Uber、Wise、xAI），只是语气加重，没有排序 |
| 2 | 什么时候该停下来问人 | **没有** | 0 处。没有任何「拿不准时…」「规范没覆盖时…」的写法 |
| 3 | 交付前自查清单 | **弱，5 家有雏形** | Cal.com、Framer、PostHog、Raycast、Superhuman 把迭代指南写成 4–5 条核查句，但只查视觉值（底色对不对、字重对不对），不查状态、溢出、可用性 |
| 4 | 验收方法（截图、对比度、溢出检查） | **没有** | 没有截图要求；没有对比度标准（全文无 WCAG、无 accessibility；contrast 出现 3 次，都指视觉反差）；overflow 只在 Tesla 一条提示词里当 CSS 属性出现。Framer、Raycast 各有 1 条以 Test 开头的条目，但没说怎么测 |
| 5 | 禁止 AI 惯性做法的清单 | **没有成形的清单，只有零散否定句** | 约 102 条迭代条目带否定，但都是品牌自己的禁忌（不用纯白、不加阴影、不用胶囊）。唯一直接点到「模型默认值」的是 MongoDB 那条（正文字重别默认用 400）。没有任何一家列「AI 常犯的通病」 |
| 6 | 组件选择决策表（什么场景用哪个组件） | **没有** | 最接近的只是「明暗区块怎么选」：HashiCorp、MongoDB（信息类用浅色、首屏和产品用深色）、Apple（沉浸用黑、说明用浅灰）、Renault（每个区块先判断明暗）、Revolut（营销用黑白、产品用语义色）。没有按钮层级、弹窗和抽屉、提示方式这类决策 |

2. 第 9、8 项。交互产品八成的工作量在表格、表单、弹窗、状态上，这些正好是材料空白的地方。
3. 第 4、3 项。没有验收方法，AI 交回来的东西好不好只能靠人眼。
4. 第 1、2 项。规则一多必然冲突，没有优先级和「停下来问」的条件，AI 会自己挑一边。
5. 第 10 项。拉丁字体的字距、大写规则直接搬到中文界面会出错，需要明确写「不适用」。
6. 第 5 项。品牌禁忌替代不了「AI 通病清单」（例如默认加渐变、默认做响应式、默认用紫蓝色、乱加阴影和图标），这部分材料里完全没有，需要自己根据踩过的坑写。

## 6. 总体评价

**判断：大约七成是前面内容的重复摘要，三成是有用的操作说明；有用的那三成集中在示例提示词里。它是「给 AI 的一页小抄」，不是「给 AI 的工作规程」。**

依据：

- **色值速查（约 17% 篇幅）**：【推断】纯摘要，不新增任何颜色，而且不完整（提示词里约 23% 的色值它没收）。作用只是省去翻模块 2 的时间。
- **迭代指南（约 30% 篇幅）**：约 86% 的条目是风格规则复述（强调色怎么用、圆角多少、字重几档），【推断】和模块 2–4、模块 7（设计护栏）高度重复。真正讲「怎么改」的约 46 条（约 14%），集中在 12 家，且是同一套模板，其中还有自相矛盾的条目。约 34 家的「迭代指南」名不副实。
- **示例提示词（约 53% 篇幅）**：这是唯一有新信息的部分。它里面的每个数值【推断】都来自模块 2–4，但它回答了前面各模块不回答的问题：这些值怎么**组合**成一个具体组件。写得好的（Kimi、IBM、Sentry、Linear、Stripe）可以直接复制去用。弱点有三个：对象偏营销页（hero 53 家，表格和弹窗 0 家）；色值写死、不引用 token；状态和尺寸大多缺失。
- **整节缺的正是「规程」部分**：优先级、何时停、怎么验收、禁止清单、决策表、token 出处，58 家里没有一家成体系地写了（第 5 节）。
- **模板化明显**：58 家三种小节、同一种句式、45 家正好 5 条、12 家的迭代条目几乎同文。【推断】这一节是按固定模板批量生成的，各家差别只在填进去的值，没有哪一家是根据「AI 实际犯了什么错」写出来的。

对用户的含义【推断】：这 58 份可以借的是**格式**（一页速查表、5 条组件配方、每条带全数值），不能借的是**内容范围**。用户要写的 Agent 指南，重点应该放在材料空白的那部分。

## 7. 写 Agent 指南的模板（10 节）

每节一句填写说明。前 4 节解决「按什么写」，中间 3 节解决「写什么」，后 3 节解决「写完怎么收」。

1. **适用范围与读者**：写明这份规范管哪些产品和界面、读者是哪些 AI（Claude Code、Codex），以及固定前提（中文界面、只做电脑版、设计宽度）。
2. **Token 的唯一来源**：写明颜色、字号、间距、圆角、阴影的变量定义在哪个文件，要求代码里只引用变量名、不写死数值，新增变量要先问。
3. **规则优先级**：列出冲突时的先后顺序（例如：用户本轮的话 > 已定内容 > 本规范的硬性规则 > 默认值 > AI 自己的审美），并标出哪些规则是硬性的。
4. **速查表**：一张 8–12 行的表，每行写「角色 → 变量名 → 当前值 → 用在哪」，覆盖背景、表面、主次文字、强调色、边框、焦点环、语义色和禁用态，明暗两套并排。
5. **组件选择决策表**：按场景写该用哪个组件（例如：确认用弹窗还是行内提示、主次按钮各在什么时候用、列表还是表格），每行一个场景、一个答案。
6. **组件配方**：给 5–8 条本产品真实组件的完整写法（窗口外壳、侧栏、列表或表格、表单、弹窗、浮窗面板），每条写全尺寸、所用变量、内部结构顺序、全部状态和真实中文文案。
7. **禁止清单**：列出 AI 的惯性做法和本产品的禁忌（例如：不加没要求的渐变和阴影、不写窄屏断点、不用拉丁字体的负字距和全大写规则、不自创颜色），每条附正确做法。
8. **什么时候停下来问**：列出必须先问人的情况（规范没覆盖的新组件、要新增变量、两条规则冲突、要改已定的样子），并写明问的格式。
9. **交付前自查与验收方法**：写成能逐条打勾的清单并说明怎么查（在真实浏览器按设计宽度截图、对比度达到多少、长中文文案不溢出不截断、每个状态都点过、没有写死的色值），以及交付时要附什么证据。
10. **修改话术**：写明提修改要求的方式（一次改一个组件、用变量名指代、症状对应修法的对照表，例如「显得挤 → 加哪一档间距」），让人和 AI 用同一套词。

【推断】说明：第 4、6、10 节在材料里有现成格式可借（分别对应速查表、示例提示词、模板 B 和 C 的迭代条目）；第 2、3、5、7、8、9 节是材料空白，需要用户按自己的产品和踩过的坑来写；第 1 节材料里也没有，但只要两三行。
